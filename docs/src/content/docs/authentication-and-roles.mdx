By the end of this page you will know how Vessel authenticates requests, when auth is required versus optional, and exactly which role every API route needs.

## JSON Web Tokens

Vessel issues a short-lived JWT (`--jwt-ttl`, default `24h`) on successful login (`POST /api/v1/auth/login`), signed with `golang-jwt/jwt/v5`. The signing key is generated once and, with `--db`, persisted; without `--db` it is regenerated on every start, which invalidates every session on restart — this is called out explicitly in the startup banner.

The console (`GET /api/v1/containers/:id/exec`) is a WebSocket, which can't carry an `Authorization` header — it instead authenticates with a one-time ticket minted by `POST /api/v1/auth/ws-ticket` and passed as a query parameter, consumed on first use.

## When auth is required

`--auth` turns login on explicitly. It also turns on **implicitly** the moment the configured store contains one or more users, even without the flag — so you can't accidentally run a database-backed Vessel wide open just by forgetting a flag on a later restart. The banner prints `auth: enabled because one or more users exist` when this implicit path fires.

<Aside type="danger" title="The Docker socket is root">
Binding a non-loopback address without `--auth` is refused outright (exit code 3) — see [Security model](/vessel/security-model/).
</Aside>

## First-run bootstrap

With `--auth` on and zero users configured, Vessel prints `no users configured — open http://<addr>:<port>/ to create the first admin account` and the UI walks you through creating that first `admin` account directly, rather than requiring a `vessel user add` on the box first.

## The three roles

Vessel's authorization model is flat and role-based, not per-resource — three roles, ranked `viewer < operator < admin`, and every route requires a minimum role:

| Role | Summary |
| --- | --- |
| `viewer` | Read everything: containers, images, volumes, networks, events, logs, stats. No mutation. |
| `operator` | Everything a viewer can, plus lifecycle actions (start/stop/restart/…), container and image file operations, image pull/tag/build/import/export, container commit and recreate, volume and network create/remove, console access, and stacks. |
| `admin` | Everything an operator can, plus prune, image removal, users, webhooks, and personal API tokens belonging to other users. |

A caller's own personal API token and password routes (`/tokens/*`, `/users/:id/password` for themselves) are available at `viewer` regardless of role, since those act on the caller's own account, not someone else's.
